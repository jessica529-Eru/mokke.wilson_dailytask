# PWA 安裝與推播：手動測試清單

自動化測試（Playwright + 預裝 Chromium）能驗證的範圍到此為止：manifest 正確、
service worker 成功註冊啟用、頁面渲染無錯誤、推播訂閱的前端流程（權限請求 →
VAPID key 轉換 → `pushManager.subscribe()` → 把 endpoint/keys 存到後端）程式碼
路徑正確無誤。

**打不到的部分是真實裝置與真實瀏覽器**：這份文件跑在沒有 GUI、沒有真實手機的
容器裡，且 Playwright 內建的 Chromium 是開源版本、沒有內嵌 Google API 金鑰，
連真的 FCM 推播伺服器做 `pushManager.subscribe()` 一律會被拒絕（
`AbortError: Registration failed`），這是瀏覽器執行檔本身的限制，不是這個
專案的程式碼問題。所以「裝置真的收到推播通知」這件事，必須由你在自己的
手機/桌機瀏覽器上實際操作才能確認。以下是完整步驟。

## 開始之前

1. **部署到 HTTPS**，或至少讓要測試的裝置能連到跑著這個 app 的
   `https://` 網址（`localhost` 在桌機瀏覽器本機測試時例外，可以直接用
   `http://localhost:3000`，但手機無法連到你電腦的 localhost，除非用
   `ngrok` 之類的工具開一個臨時 HTTPS 通道，或部署到一個有 HTTPS 的地方）。
   PWA 安裝與 Web Push 都要求安全連線（secure context），這不是這個專案
   能繞過的瀏覽器規範。
2. 確認 `.env` 裡 `NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` /
   `VAPID_SUBJECT` 都已設定（見 README「Web Push」小節），否則推播會整組
   靜默不生效（站內通知仍正常）。
3. 建議兩個人各自用自己的手機或電腦，一人建房、一人加入，這樣才能實際
   測到「對方觸發事件、我收到推播」的完整場景。

## 桌面瀏覽器（Chrome / Edge）

1. 開啟網址，右上角網址列應該會出現一個「安裝」圖示（或選單 → 安裝
   應用程式）。點下去，確認出現安裝對話框、app 名稱與圖示正確。
2. 安裝後從開始選單/應用程式列表開啟，應該是獨立視窗（無網址列），
   對應 `manifest.json` 的 `display: standalone`。
3. 進入任一房間頁面，右上角點「🔕 啟用推播通知」，瀏覽器應該跳出通知
   權限請求，允許後按鈕文字要變成「🔔 推播已啟用」。
4. 讓房間裡的另一人（另一台裝置或無痕視窗登入另一帳號）觸發一個會通知你
   的動作，例如幫你的任務按核准、加碼、或觸發驚喜任務。
5. 你這邊應該在幾秒內收到瀏覽器系統通知（即使分頁不在前景，甚至瀏覽器
   縮到背景，只要瀏覽器行程還在跑）。點通知應該會開啟或聚焦到通知頁
   （`/rooms/:id/notifications`）。
6. 反例測試：把裝置切成飛航模式或關網路，觸發同一動作，確認站內通知
   （左上角「通知」分頁）還是正常記錄了這筆，沒有因為推播失敗而遺漏。

## 桌面 Safari（macOS）

Safari 16.4+ 才支援 Web Push，且步驟跟 Chrome 系略有不同（可能需要先把
網站加到「加入太多」或透過選單「檔案 → 加入到 Dock」安裝成 app 再啟用
通知）。這條路徑目前沒有實機驗證，建議你實測時特別留意：如果通知權限
按鈕點了沒反應或沒跳出權限請求，很可能是 Safari 版本太舊或還沒安裝成
app，這是 Safari 自己的限制，不代表程式碼有問題。

## 手機 Android（Chrome）

1. 用 Chrome 開啟網址，選單（右上角三點）應該會有「新增至主畫面」或
   「安裝應用程式」選項。
2. 安裝後從主畫面圖示開啟，應為全螢幕獨立體驗（沒有網址列）。
3. 房間頁面點「啟用推播通知」，允許系統通知權限。
4. 讓對方觸發一個通知事件，確認手機在**背景**（按 Home 鍵、甚至完全關閉
   分頁）時仍然跳出系統通知橫幅、有聲音/震動（依系統設定），點通知能
   開啟 app 並跳到通知頁。

## 手機 iOS（Safari）

iOS 對 Web Push 的支援天生比較有限，這也是規格書第 12 節技術棧特別註記
「iOS PWA 推播支援有限，需搭配站內未讀提示備援」的原因，這個 app 已經
把站內通知中心做成獨立於推播之外的完整備援：

1. **一定要先「加入主畫面」**（分享圖示 → 加入主畫面）——iOS 16.4 以前完全
   不支援網頁推播；16.4 之後，**只有從主畫面圖示開啟的 PWA 才能訂閱推播**，
   在 Safari 分頁裡直接點「啟用推播通知」大概率沒反應或直接失敗。
2. 從主畫面圖示開啟後，再點推播開關、允許通知權限。
3. 觸發對方的通知事件，確認鎖定畫面/通知中心有跳出系統通知。
4. 如果怎麼測都收不到，屬於 iOS 平台已知限制範圍，站內通知（頁面上的
   「通知」分頁 + 未讀提示）就是這裡設計上預期的備援路徑，不需要為了
   凑合 iOS 推播去改動架構。

## 判斷「測試通過」的標準

- manifest/service worker/安裝流程：跟第一節自動化測試結果一致就算過，
  不需要每個瀏覽器都重測。
- 推播：**任一個桌面 Chrome/Edge 環境**能跑完「訂閱 → 對方觸發 → 收到系統
  通知」全程，就代表伺服器端（`lib/push.ts` / VAPID 設定 / service worker
  的 `push` handler）是正確接通的；iOS/Safari 測不過通常是平台限制，不是
  程式碼問題，可以放心把站內通知當作那些情境下的正式體驗。
